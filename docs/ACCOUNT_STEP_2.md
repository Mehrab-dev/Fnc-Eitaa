# گام ۲ — هستهٔ ارتباط اکانت

وضعیت در ۱۵ اکتبر ۲۰۲۶: پیاده‌سازی پایه و تست‌های محلی انجام شد؛ بررسی واقعی
درخواست بدون ورود نیز پاسخ مورد انتظار را داد. ورود موفق اکانت هنوز انجام نشده است.

## این گام چه کاربردی دارد؟

در گام قبل فهمیدیم ایتا داده‌ها را چگونه مبادله می‌کند. در این گام کدی نوشتیم که
همان قالب را تولید و پردازش می‌کند: مثلاً نام متد و پارامترهای پایتون را به بایت
تبدیل می‌کند، درخواست را به سرور می‌فرستد و پاسخ باینری را به داده یا خطای مشخص
پایتون برمی‌گرداند. ورود، ارسال پیام از اکانت و دریافت رویدادهای مراحل بعد روی
این هسته ساخته خواهند شد.

هستهٔ اکانت مستقل از ارسال با توکن ایتایار است. رابط `Client` قبلی فعلاً همان
کاربرد توکن/صفحات عمومی را دارد؛ برای این مرحله رابط آزمایشی جدا داریم.

## چه چیزهایی ساخته شد؟

| بخش | فایل | کارکرد |
| --- | --- | --- |
| schema نسخه‌بندی‌شده | `fnceitaa/protocol/schema.py` و `schema.json` | پیدا کردن شناسه، نوع و ترتیب فیلدها بدون نیاز به اینترنت |
| codec باینری | `fnceitaa/protocol/codec.py` | نوشتن و خواندن نوع‌های پایه، دادهٔ تو در تو و پاسخ فشرده |
| transport اکانت | `fnceitaa/account.py` | ساخت `eitaaObject`، HTTP و تطبیق پاسخ با درخواست |
| هماهنگ‌سازی دادهٔ منبع | `scripts/sync_protocol.py` | نگه داشتن schema بسته مطابق snapshot بررسی‌شده |
| نمونهٔ اجرا | `examples/account_transport.py` | مشاهدهٔ بسته و بررسی فقط‌خواندنی با توکن خالی |

codec نوع‌های `int`، `long`، `double`، اعداد ثابت به شکل بایت، متن UTF-8، bytes،
Bool، vector، فیلدهای اختیاری و queryهای جنریک را پوشش می‌دهد. برای query از
`TLCall` استفاده می‌شود؛ کد دلخواه یا تابع دریافتی از منبع اجرا نمی‌شود.

برای constructorهای دارای نام تکراری، نوشتن مطابق اولین ورودی نام و خواندن مطابق
آخرین ورودی شناسه در همان namespace است؛ این سیاست از کلاینت بررسی‌شده می‌آید.
نوع bare مبهم حدس زده نمی‌شود. پشتیبانی قالب‌های عمومی به معنی تأیید تک‌تک
متدهای schema روی سرور واقعی نیست.

## نتیجهٔ آزمایش‌ها

- بستهٔ تولیدشده با codec دقیقاً با بستهٔ ثبت‌شدهٔ گام ۱ برابر شد.
- پاسخ واقعی گام ۱ به `AccountRPCError(401, INVALID_LOGIN)` تبدیل شد.
- نمونهٔ جدید با همین transport روی سرور اجرا شد و همان خطا را دریافت کرد.
- هر **۶۷ تست** محلی پاس شدند؛ تست‌های خودکار شبکه یا OTP واقعی استفاده نمی‌کنند.
- wheel ساخته شد؛ schema و تنظیمات پروتکل در بسته قرار می‌گیرند.

خطای `INVALID_LOGIN` در این بررسی انتظار می‌رود: عمداً توکن خالی و شناسهٔ دستگاه
آزمایشی داریم. نتیجه نشان می‌دهد قالب درخواست تا بررسی احراز هویت پذیرفته شده
است؛ ورود موفق یا دریافت اطلاعات خصوصی را اثبات نمی‌کند.

## چطور امتحان کنیم؟

از پوشهٔ اصلی پروژه، در محیط پایتون دارای وابستگی‌ها:

```powershell
python -m examples.account_transport
```

این دستور فقط بسته را چاپ می‌کند و درخواست شبکه ندارد. برای ارسال همین درخواست
فقط‌خواندنی با توکن خالی:

```powershell
python -m examples.account_transport --live
```

خروجی مورد انتظار شامل `401 / INVALID_LOGIN` است. این نمونه شماره تلفن، OTP
و توکن شخصی نمی‌گیرد و ورود انجام نمی‌دهد.

نمونهٔ استفادهٔ داخلی از codec:

```python
from fnceitaa.protocol import TLCodec

codec = TLCodec()
packet = codec.encode_method("updates.getState")
print(packet.hex())  # 2a88d4ed

error = codec.decode(bytes.fromhex(
    "bbf9b9c4910100000d494e56414c49445f4c4f47494e0000"
))
print(error["code"], error["text"])
```

## پاسخ‌ها و خطاها چه رفتاری دارند؟

- `AccountReply` نتیجه، شناسهٔ محلی درخواست و به‌روزرسانی‌های همراه را نگه می‌دارد.
- `pong` و توکن تمدیدشده در `control` مشخص می‌شوند؛ رسید کنترلی به معنی موفقیت
  عملیات یا ارسال OTP نیست. تفسیر آن برای ورود به گام ۳ تعلق دارد.
- `rpc_result` باید متعلق به همان درخواست باشد. container فاقد نتیجه، دارای
  نتیجهٔ تکراری یا نامرتبط پذیرفته نمی‌شود. بدنهٔ هر پیام container مرز بایتی دارد.
- انقضا/درحال‌تمدیدبودن توکن با `AccountStateError` گزارش می‌شود؛ تمدید خودکار
  در این مرحله وجود ندارد.
- خرابی قالب، دادهٔ ناقص و عبور از حدود با `TLCodecError` رد می‌شوند.
- خطای HTTP با `AccountTransportError` و خطای سرور با `AccountRPCError` گزارش می‌شود.
  متن دلخواه سرور و URL خطای requests در پیام خطا بازتاب داده نمی‌شوند.
- درخواست‌ها به ترتیب ارسال می‌شوند و تکرار خودکار ندارند. timeout یا لغو یک
  ارسال ممکن است نتیجهٔ نامعلوم داشته باشد؛ نباید آن را موفقیت یا عدم ارسال قطعی دانست.
- لغو await درخواست HTTP ارسال‌شده را پس نمی‌گیرد. تا خروج worker، نوبت درخواست
  بعدی آزاد نمی‌شود؛ لغو درخواستِ منتظر صف مانع ارسال همان درخواست می‌شود.

## حدود پیش‌فرض

| مورد | حد |
| --- | --- |
| بستهٔ ورودی یا خروجی | ۸ MiB |
| یک رشته یا bytes | ۴ MiB |
| تعداد اعضای یک vector | ۱۰۰٬۰۰۰ |
| عمق پردازش | ۶۴ |
| بودجهٔ گره‌های پردازش | ۲۰۰٬۰۰۰ |
| مجموع خروجی بازشدهٔ gzip در یک decode | ۸ MiB |
| timeout اتصال | ۱۰ ثانیه |
| timeout هر خواندن شبکه | ۱۰ ثانیه |
| بررسی زمان سپری‌شده هنگام دریافت | ۳۰ ثانیه |

بررسی زمان سپری‌شده بین خواندن‌ها انجام می‌شود؛ یک خواندن مسدودشده می‌تواند تا
timeout خواندن ادامه پیدا کند. این محدودیت معادل لغو قطعی worker در ثانیهٔ ۳۰ نیست.
حدود codec با `Limits` قابل تنظیم هستند. مسیر HTTP به HTTPS دامنه‌های ایتا محدود
است و redirect دنبال نمی‌شود. انتخاب خودکار سرور جایگزین هنوز اضافه نشده است.

## بررسی توسعه و بسته‌بندی

```powershell
python -m unittest discover -s tests -v
python scripts/sync_protocol.py --check
python -m pip wheel . --no-deps --wheel-dir dist
```

پس از بررسی و به‌روزرسانی snapshot پژوهشی، با `python scripts/sync_protocol.py`
منابع داخل بسته را هماهنگ کنید. ساخت wheel به فایل JavaScript یا پوشهٔ پژوهش
وابسته نیست؛ دادهٔ لازم داخل پکیج قرار دارد.

## مرحلهٔ بعد

گام ۳ جریان ورود واقعی را اضافه می‌کند: ساخت شناسهٔ دستگاه، درخواست کد، ورود،
مسیر رمز دوم و ذخیرهٔ اتمیک `account.session`. معیار پایان آن، ورود تازه و سپس
شناخت همان اکانت در اجرای بعدی با سشن ذخیره‌شده است.
