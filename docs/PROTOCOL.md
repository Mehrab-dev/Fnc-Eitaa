# Eitaa account protocol: versioned research baseline

Observed on 2026-10-15. This is an implementation specification derived from
public client code plus one unauthenticated, read-only request. It is not a
claim of working account authentication.

## Confidence levels

- **Static observation:** code and tables present in the pinned public client.
- **Wire observation:** the exact request and response recorded in
  `research/protocol/public_probe.json`.
- **Unverified:** successful authentication and all authenticated operations.

A schema entry, web fallback, or local response is not server acceptance.

## 1. Transport and endpoint selection

Evidence anchors: `http_post`, `blocked_methods`; inventory: `server_pools`.

The observed client uses HTTPS POST with binary body, reads `arrayBuffer()`,
and aborts an individual HTTP call after 30 seconds. It does not require a
JSON REST route per method. The configuration forces HTTP; its socket selector
has no implementation in this version. This does not prove the service has no
other transports.

Separate pools exist for normal RPC, upload and download. The full candidates
are in the inventory. The client filters failed servers and randomly chooses
from the remaining pool, resetting the filter when all candidates fail. That
behavior is observed source code, not a recommendation for automatic retries.

Only `https://hasan.eitaa.ir/eitaa/` was probed in this research. Endpoint
availability, redirects, rate limits and cross-server session behavior remain
unverified. Use certificate verification and bounded response sizes in the SDK.

## 2. Binary primitives

Evidence anchors: `integer_layout`, `tl_strings`, `tl_flags`, `tl_objects`.

The client writes 32-bit words through typed arrays and long values as low
32-bit word followed by high 32-bit word. The recorded little-endian packet
was accepted as far as authentication checking. The Python codec should use
explicit little-endian encoding and Python integers to avoid precision loss.

Strings are UTF-8, followed by the TL bytes length/padding representation:

- 0..253 bytes: one length byte, then data.
- 254 or more: byte `254`, then three little-endian length bytes, then data.
- Add zero padding to align the whole encoded value to four bytes.

`bytes` uses the same length/padding but has no UTF-8 conversion. Constructor
and method IDs occupy 32 bits; JSON may represent them as negative signed
integers. Preserve their bit pattern. Vector constructor ID is `0x1cb5c415`;
boxed `Vector<T>` and bare `vector<T>` are distinct. Bare `%Type` fields and
generic `!X` queries require explicit support, not ordinary dictionary encoding.

`#` fields are computed optional-field masks in the observed serializer;
`flags.N?true` contributes a bit without a payload. Not every field called
`flags` is a mask: `eitaaObject.flags` has type `int` and must be sent literally.

The reader selects MTProto constructors first and can fall back to the API
constructor table. It has special handling for vectors, gzip, bare types and
RPC results. Implement bounds, recursion, vector-count and decompression limits
before treating remote data as safe to decode.

## 3. Eitaa request envelope

Evidence anchors: `request_envelope`, `api_wrapping`.

When no MTProto auth key is present, the code serializes the API method directly
and wraps its bytes in the API method `eitaaObject` (`0x7abe77ed`):

| Order | Name | Wire type | Observed value/meaning |
| --- | --- | --- | --- |
| 1 | token | string | Empty before login; account token afterward |
| 2 | imei | string | Device identifier generated by the client |
| 3 | packed_data | bytes | Serialized API call |
| 4 | layer | int | 135 |
| 5 | flags | int | 128 |

Despite the function name `getEncryptedOutput`, this branch does not use the
MTProto auth-key encryption path. HTTPS still protects the connection. Do not
add Telegram key exchange merely because the bundle also contains that code.

`invokeWithLayer` and `initConnection` are used in the other auth-key branch;
the no-authKey branch calls `storeApiCall` directly. Revalidate this distinction
when implementing initialization. Public app configuration also changes API
identity for the main web domain (`domain_api_config` evidence). Do not blindly
reuse an environment fallback API ID or assume public app identity guarantees
permission for an independent client.

## 4. Response and correlation

Evidence anchors: `response_decoding`, `response_correlation`, `tl_objects`.

In the no-authKey branch the HTTP response is decoded directly as a TL object;
the normal encrypted MTProto response header is not consumed. The HTTP handler
associates the response with the locally tracked outgoing message ID. This ID
is not one of the outer `eitaaObject` fields.

The tables include `rpc_result`, `rpc_error`, `pong`, `msg_container`, gzip,
API `error` and API `eitta_error`. The general RPC path has per-request result
types. Do not assume every success is a dictionary or that every response is
wrapped by `rpc_result`. Vector-valued responses need the expected return type.
Serialize initial account RPCs sequentially until response correlation and
containers are acceptance-tested.

## 5. Phone login state machine

Static observations from the login/code chunks and anchors `otp_ack`,
`authorization_and_errors`, `device_identifier`, `two_step_password`:

1. Normalize the phone number and create/persist the device identifier before
   `auth.sendCode`.
2. Send `auth.sendCode` (`0xa677244f`), with `phone_number`, `api_id`, `api_hash`,
   and a `codeSettings` object (`0xdebebe83`; optional flags are empty in the UI).
3. Handle a real `auth.sentCode` and the web client's special `pong` branch:
   for a pending `auth.sendCode`, the client locally constructs a six-digit SMS
   receipt and uses `String(outgoing_message_id)` as `phone_code_hash`.
   This is a local compatibility path, not proof that every server response
   uses it. Never claim an OTP was sent merely because a pong was decoded for
   some unrelated request.
4. Submit `auth.signIn` (`0xbcd51581`) with the same phone, receipt hash and OTP.
5. On `auth.authorization` (`0xcd050916`), consume flags, token and User; persist
   the new SDK session only after validated authorization.
6. On `SESSION_PASSWORD_NEEDED`, continue the verified password flow. The worker
   supports an `account.password2` salted-password branch (`auth.checkPassword2`)
   as well as an SRP branch (`auth.checkPassword`). Step 3 implements and locally
   tests both derivations; the server's actual choice still needs live acceptance.
   Additional source hashes/offsets are in `auth_evidence.json`, including the
   password page and crypto worker. See [ACCOUNT_STEP_3.md](ACCOUNT_STEP_3.md).

Phone-derived device ID in the observed source: remove nondigits, then an
initial `00`; hash the resulting text with SHA-256; use a leading hex substring
plus the last eight base-36 digits of milliseconds, base-36 account index, and
`__web`, for a total length of 20 characters. This is a static observation.
Define Unicode digit handling and stable per-session identity explicitly in
Python. No phone or OTP was supplied during this research.

## 6. Session and token renewal

Evidence anchors: `device_identifier`, `authorization_and_errors`, `token_refresh`.

The observed web account state includes a token, device ID and account/DC
metadata. SDK session persistence must be independent of browser storage and
separate from Eitaayar tokens. No browser cookies, profile/session databases or
local storage were inspected.

`eitaa_updates_expire_token` (`0xdc252379`) and `eitaa_token_updating`
(`0xdc252375`) pause the observed sender and trigger renewal. The renewal call
is `eitaaRefreshToken` (`0xdc452369`), with `eitaaAppInfo`. Its fields include
build/app/device/system/language information and `sign`. The source constructs
`sign` as an empty string here; this remains unverified on a fresh SDK login.
The expected `eitaa_updates_token` (`0xa56c1a31`) contains token, expire and date.

Step 3 stores version, token, device ID, numeric user ID, endpoint and API ID.
It uses a single-account index for device generation, keeps no unverified expiry
metadata, and never persists OTP or passwords. Atomic file replacement,
permissions, corruption/version checks and a one-refresh retry bound are
implemented; live authenticated acceptance remains pending. The session is
independent of browser credentials and is not encrypted.

## 7. Errors, fallbacks and capability pitfalls

Inventory contains 443 API method entries, 990 API constructor entries, 12
MTProto method entries and 52 MTProto constructor entries. Counts include
source duplicates. Constructor names such as `chatPhoto` and `photoSize` occur
with different IDs; two MTProto advertising entries use `method` instead of
`predicate`. Preserve and report those anomalies rather than silently fixing
the upstream schema. Index decoding by ID with a documented conflict policy.

The `eitaaNoSend` array has 78 entries (including duplicates). The API manager
can synthesize empty/placeholder responses; the networker also rejects blocked
calls. Examples include QR export, some reactions and sticker APIs. This is a
web-client policy, not proof of permanent server impossibility, but the SDK
must not advertise those capabilities based on schema presence alone.

The error handlers recognize auth errors, migration, flood waits and server
errors. `INVALID_LOGIN` can trigger token refresh/retry in the web client; it
limits consecutive invalid-login refreshes. Model expiry vs revoked login,
flood-wait duration and uncertain send outcomes separately. Do not copy blanket
web retries for sends, as their outcomes can be ambiguous.

## 8. Live read-only framing fixture

One unauthenticated POST to the observed normal RPC server sent
`updates.getState` (`0xedd4882a`) inside the envelope above, with empty token
and a synthetic device string. This call supplies no phone, OTP, credentials
or real account identity and cannot read private account state without login.

Recorded result: HTTP 200, `application/octet-stream`, 24 bytes. Decoded fields:

| Field | Value |
| --- | --- |
| API constructor | `error`, `0xc4b9f9bb` |
| code | 401 |
| text | `INVALID_LOGIN` |

The fixture stores the complete request and response bytes, not a manufactured
success. It confirms this request reached authentication checking and this
error encoding matches the schema. It does not validate successful method
execution, token validity, login, OTP receipt behavior or other endpoints.

## 9. Exit criteria and next implementation

Completed research baseline: source hashes, repeatable schema extraction,
selected IDs and field order, server pools, packet/response evidence, login
branches, token lifecycle, unsupported web methods and explicit unknowns.

Step 2 implemented an internal TL codec and bounded account HTTP transport.
It reproduces the recorded request and decodes the recorded/live empty-token
error. See [ACCOUNT_STEP_2.md](ACCOUNT_STEP_2.md). Validation began with
hand-reviewed primitive fixtures and the recorded error packet, then covered
nested/vector/flags/container/gzip responses. Before the account API is usable,
perform a fresh authorized OTP login and reconnect from its saved SDK session.
Keep successful authenticated capture and acceptance as a later milestone;
step 1 is complete as a research baseline, not as a working account client.
