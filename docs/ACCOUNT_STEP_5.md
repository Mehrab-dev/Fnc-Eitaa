# گام ۵ — متن، ریپلای و تاریخچهٔ اکانت

این گام روی `AccountClient` کار می‌کند و از سشن اکانت شخصی استفاده می‌کند.
ارسال با توکن ایتایار در `Client` مسیر جداگانه‌ای است.

## امکانات

| متد | کاربرد |
| --- | --- |
| `send_message(peer, text, reply_to_msg_id=None, ...)` | ارسال یک متن ساده یا ریپلای به پیام همان مقصد |
| `get_message(peer, message_id)` | خواندن پیام مشخص؛ پیام خالی/حذف‌شده/متعلق به چت دیگر: `None` |
| `get_history(peer, limit=100, offset_id=0)` | فهرست پیام‌ها از جدید به قدیم |
| `iter_history(peer, limit=None, page_size=100, offset_id=0)` | خواندن تدریجی تاریخچه |
| `get_history_page(peer, limit=100, offset_id=0)` | یک صفحه همراه `next_offset_id` و شمارش گزارش‌شدهٔ سرور |

مقصد می‌تواند `self`، نام کاربری، `AccountPeer` یا هویت عددی شناخته‌شده در
کش گام ۴ باشد. برای کاربر/کانال خصوصی در یک اجرای تازه، ابتدا گفتگوها را
بخوانید؛ access hash ناشناخته حدس زده نمی‌شود.

خروجی `AccountMessage` شامل `id`، `peer`، `date`، `text`، `outgoing`،
`reply_to_msg_id`، `sender`، `is_service` و `has_media` است. نتیجهٔ ارسال
`random_id` عملیات را هم دارد. متن و random ID در repr پیام چاپ نمی‌شوند.
وجود مدیا صرفاً مشخص می‌شود؛ آپلود/دانلود مربوط به گام ۸ است.

## آزمایش خواندن

```powershell
python -m examples.account_messages history --live --peer "@eitaa" --limit 5
python -m examples.account_messages history --live --peer "@eitaa" --limit 5 --show-text
```

یک شناسه از خروجی بگیرید و فقط همان پیام را بخوانید؛ `123` مثال است:

```powershell
python -m examples.account_messages read --live --peer "@eitaa" --message-id 123 --show-text
```

متن‌ها تنها با `--show-text` نمایش داده می‌شوند و نویسه‌های کنترلی به شکل
JSON escape می‌شوند. متدهای خواندن درخواست علامت‌زدن پیام به‌عنوان خوانده‌شده
نمی‌فرستند. نمونه بدون `--live` سشن را باز نمی‌کند و هیچ درخواستی نمی‌فرستد.

## آزمایش ارسال در ترمینال خودتان

برای شروع، فقط به خودتان بفرستید:

```powershell
python -m examples.account_messages send --live --peer self
```

نمونه متن را می‌پرسد، مقصد و متن و random ID را نشان می‌دهد و فقط پس از
نوشتن دقیق `yes` یک ارسال انجام می‌دهد. سپس باید `Send confirmed` همراه
شناسهٔ پیام ببینید. ارسال زنده توسط عامل توسعه انجام نشده است.

برای ریپلای، شناسهٔ همان پیام ارسالی را جایگزین `123` کنید:

```powershell
python -m examples.account_messages send --live --peer self --reply-to 123
```

برای مقصد خصوصی شناخته‌شده در گفتگوها، می‌توان از
`--load-dialogs --peer user:ID` یا `--load-dialogs --peer channel:ID` استفاده
کرد. این گزینه تا ۱۰۰۰ گفتگو را پیش از resolve در کش می‌گذارد. در دسترس بودن
هویت مقصد به‌معنای مجوز ارسال نیست؛ سرور مجوز ارسال را بررسی می‌کند.

## استفاده از کتابخانه

این قطعه در صورت اجرا یک پیام واقعی به حساب خودتان می‌فرستد:

```python
import asyncio
import secrets
from fnceitaa import AccountClient, SendMessageUncertainError

async def main():
    async with AccountClient('account.session') as client:
        operation_id = secrets.randbits(63) or 1
        # برای بازیابی پس از بسته‌شدن برنامه، شناسهٔ عملیات را پیش از ارسال
        # در محل مناسب برنامهٔ خودتان ثبت کنید.
        try:
            sent = await client.send_message('self', 'سلام', random_id=operation_id)
        except SendMessageUncertainError as error:
            print('نتیجه نامعلوم؛ قبل از تکرار، مقصد را بررسی کنید.', error.random_id)
            return
        print('شناسهٔ تأییدشده:', sent.id)
        message = await client.get_message('self', sent.id)
        print('قابل خواندن:', message is not None)

asyncio.run(main())
```

## ارسال و نتیجهٔ نامعلوم

- `random_id` یک عدد غیرصفر signed 64-bit است. در صورت نبودن، با CSPRNG
  ساخته می‌شود. آن را برای عملیات منطقی دیگری یا متن/مقصد متفاوت دوباره استفاده نکنید.
- پاسخ `updateShortSentMessage` یا نگاشت دقیق `updateMessageID` با همان
  random ID تأیید محسوب می‌شود. `pong` یا یک update خروجی نامرتبط موفقیت نیست.
- قطع شبکه، پاسخ خراب یا پاسخ بدون تأیید، `SendMessageUncertainError` می‌دهد؛
  ممکن است پیام روی سرور ثبت شده باشد. خطا random ID را حفظ می‌کند و متن را چاپ نمی‌کند.
- لغو هنگام اجرای RPC با `SendMessageCancelledError` که زیرکلاس
  `asyncio.CancelledError` است منتقل می‌شود؛ random ID روی خطا موجود است.
- هیچ ارسال یا ریپلای به‌صورت خودکار تکرار نمی‌شود؛ حتی در سیگنال انقضای توکن.
  خطاهای صریح سرور مثل محدودیت ارسال و flood wait به برنامه برمی‌گردند.
- برای ارسال مجددِ نامعلوم، ابتدا مقصد را بررسی کنید. اگر آگاهانه همان عملیات
  را دوباره امتحان می‌کنید، random ID و متن و مقصد را ثابت نگه دارید؛ طول عمر و
  رفتار dedup سرور ایتا در این پروژه تضمین نشده است. صف پایدار و بازیابی پس از
  crash در گام ۱۰ پیاده خواهد شد.

## حدود پیاده‌سازی

- ارسال ساده تا ۴۰۹۶ واحد UTF-16؛ این سقف محلی SDK است و متن بلند خودکار
  تکه‌تکه نمی‌شود. قالب‌بندی Markdown/HTML، entity سفارشی، زمان‌بندی، ارسال
  مدیا و ریپلای بین دو چت در این گام اضافه نشده‌اند.
- `silent` و `no_webpage` پشتیبانی می‌شوند؛ نمونهٔ ترمینال preview لینک را غیرفعال می‌کند.
- پیام‌های کانال/سوپرگروه با `channels.getMessages` و بقیه با
  `messages.getMessages` خوانده می‌شوند. شناسهٔ درست در چت اشتباه داده نمی‌شود.
- تاریخچه جدید به قدیم است؛ offset مثبت انحصاری است. پیام‌های خالی نمایش
  داده نمی‌شوند ولی cursor را جلو می‌برند. پاسخ با مقصد/offset نامرتبط، خطا
  می‌دهد تا پیام اشتباهی نمایش داده نشود یا حلقهٔ بی‌پایان ایجاد نشود.
- سرور ممکن است بیش از اندازهٔ درخواستی صفحه بدهد؛ iterator و get_history
  سقف limit خروجی را رعایت می‌کنند. صفحهٔ خام تمام نتیجهٔ سرور را حفظ می‌کند.
- داده‌های پیام و peer در حافظه‌اند؛ کش دائمی، رویداد زنده و SQLite هنوز مربوط
  به فازهای بعد هستند. تغییر هم‌زمان تاریخچه در سرور snapshot تضمین‌شده نمی‌دهد.

## شواهد و پذیرش

در ۱۷ اکتبر ۲۰۲۶، با سشن موجود، سه پیام از کانال عمومی `@eitaa` خوانده شد؛
خواندن یک پیام با شناسه و خواندن سه پیام صفحهٔ بعد با offset قدیمی‌تر هم موفق
بود. متن یا شناسهٔ پیام‌های خصوصی و توکن در شواهد ذخیره نشدند. هیچ ارسال زنده
یا درخواست OTP انجام نشد.

ارسال و ریپلای با پاسخ‌های باینری شبیه‌سازی‌شده و سناریوهای قطع ارتباط، لغو،
شناسهٔ تصادفی نامرتبط، پاسخ ناقص، مجوز ردشده و flood wait تست می‌شوند.
کاربر سپس نمونه‌ها را روی حساب خود اجرا کرد و این موارد تأیید شدند:

- ارسال متن به خود و دریافت شناسهٔ تأییدشدهٔ پیام.
- خواندن همان پیام با متن یکسان و وضعیت خروجی.
- ارسال پیام دوم به‌صورت ریپلای و خواندن مجدد آن با شناسهٔ ریپلای درست.
- دریافت تاریخچهٔ خود به ترتیب جدید به قدیم با حفظ ارتباط ریپلای.

بنابراین پذیرش زندهٔ این مسیرهای گام ۵ انجام شد. ارسال به کاربر دیگر، گروه
معمولی و کانال هنوز جداگانه آزمایش نشده است. اطلاعات خصوصی حساب و شناسه‌های
پیام‌های خود کاربر در مستندات و شواهد ثبت نشده‌اند.
