# گام ۴ — هویت مقصدها و فهرست گفتگوهای اکانت

این گام به برنامه اجازه می‌دهد نام کاربری را به هویت واقعی مقصد تبدیل کند و
گفتگوهای حساب واردشده را بخواند. مقصد شامل نوع، شناسه و در صورت نیاز
`access_hash` است؛ شناسهٔ عددی تنها، اطلاعات کافی برای همهٔ عملیات نیست.

ورود OTP، ذخیرهٔ سشن و reconnect بدون OTP در گام قبل توسط کاربر تأیید شدند.
ورود واقعی با رمز دوم، انقضا و لغو سشن هنوز پذیرش زندهٔ جداگانه می‌خواهند؛
تست‌های محلی این مسیرها جای پذیرش زنده را نمی‌گیرند.

## اجرای نمونه

از سشن موجود استفاده کنید:

```powershell
python -m examples.account_dialogs --live
python -m examples.account_dialogs --live --peer "@eitaa"
python -m examples.account_dialogs --live --folder archive
```

خروجی پیش‌فرض نوع و شناسهٔ مقصد، تعداد خوانده‌نشده‌ها و وضعیت پین را نشان
می‌دهد. برای نمایش نام‌ها در ترمینال خودتان، `--show-titles` را اضافه کنید.
متن پیام‌ها و `access_hash` چاپ نمی‌شوند. بدون `--live` فایل سشن باز نمی‌شود
و شبکه استفاده نمی‌شود. نبودن سشن باعث درخواست خودکار کد ورود نمی‌شود.

## استفاده در برنامه

```python
import asyncio
from fnceitaa import AccountClient

async def main():
    async with AccountClient('account.session') as client:
        myself = await client.resolve_peer('self')
        channel = await client.resolve_peer('@eitaa')
        print(channel.kind.value, channel.id)

        async for dialog in client.iter_dialogs(limit=200, page_size=100):
            print(dialog.peer.kind.value, dialog.peer.id, dialog.unread_count)
            # اطلاعات همین گفتگو در کش حافظه‌ای اکانت قابل استفاده است.
            peer = await client.resolve_peer(
                f'{dialog.peer.kind.value}:{dialog.peer.id}')

asyncio.run(main())
```

| متد / مدل | کاربرد |
| --- | --- |
| `resolve_peer('me' / 'self')` | هویت حساب جاری |
| `resolve_peer('@username')` | درخواست واقعی `contacts.resolveUsername` |
| `resolve_peer(id)` | مقصد شناخته‌شده در کش؛ برخورد نوع‌ها خطا می‌دهد |
| `resolve_peer('user:ID' / 'channel:ID')` | انتخاب نوع صریح از کش |
| `resolve_peer('chat:ID')` | ساخت هویت گروه معمولی بدون حدس access hash؛ وجود گروه را تأیید نمی‌کند |
| `resolve_peer(AccountPeer(...))` | استفاده از هویت صریح مربوط به همین حساب |
| `get_dialogs(limit=100, folder_id=None)` | لیست حداکثر limit گفتگو |
| `iter_dialogs(limit=None, page_size=100, folder_id=None)` | دریافت تدریجی با حذف تکراری‌ها |
| `get_dialogs_page(limit=100, cursor=None, folder_id=None)` | یک صفحه همراه `next_cursor` و `total_count` |
| `AccountPeer.to_input_peer()` | تبدیل به ساختار ورودی پروتکل |

`PeerKind.USER` کاربر، `PeerKind.CHAT` گروه معمولی و `PeerKind.CHANNEL`
کانال یا سوپرگروه است؛ `is_megagroup` سوپرگروه را مشخص می‌کند.
`folder_id=None` همه، `0` اصلی و `1` بایگانی است. بین صفحه‌ها folder_id را
ثابت نگه دارید. `total_count` شمارش گزارش‌شدهٔ سرور است و ممکن است خلاصهٔ
پوشه‌ها را نیز شامل شود؛ این خلاصه‌ها در لیست گفتگوها برگردانده نمی‌شوند.

## قواعد و محدودیت‌ها

- هویت‌ها به اکانت وابسته‌اند؛ `AccountPeer` و cursor را بین حساب‌ها جابه‌جا نکنید.
- کش حداکثر ۱۰ هزار هویت دارد و با disconnect پاک می‌شود. ذخیرهٔ دائمی کش
  در گام SQLite انجام می‌شود. شناسهٔ ناشناخته خودکار به کاربر یا کانال حدس زده نمی‌شود.
- access hash مفقود یا هویت `min` برای کاربر/کانال به صفر تبدیل نمی‌شود؛
  `PeerResolveError` می‌گیرید. اطلاعات کامل کش با نسخهٔ min جایگزین نمی‌شود.
- `get_dialogs_page` نتیجهٔ واقعی صفحه را برمی‌گرداند؛ سرور ممکن است بیشتر از
  limit درخواستی برگرداند. `get_dialogs` و `iter_dialogs` سقف خروجی را رعایت می‌کنند.
- صفحهٔ بعد با تاریخ پیام آخر، شناسهٔ پیام و هویت همان گفتگو ساخته می‌شود.
  یکسان‌بودن شناسهٔ پیام در دو چت باعث انتخاب تاریخ چت دیگر نمی‌شود.
- گفتگوهای پین‌شده در صفحهٔ اول حفظ می‌شوند؛ ادامه با exclude_pinned و کنترل
  cursor تکراری انجام می‌شود. cursor نامعتبر یا نبودن تاریخ لازم خطا می‌دهد؛
  نتیجه به‌اشتباه «فهرست کامل» اعلام نمی‌شود. تغییر هم‌زمان گفتگوها در سرور
  همچنان می‌تواند ترتیب را جابه‌جا کند؛ این فهرست snapshot تراکنشی نیست.
- خواندن فقط در سیگنال صریح انقضای توکن، یک بار پس از نوسازی تکرار می‌شود.
  Flood wait یا خطای شبکه باعث retry خودکار نمی‌شود. سشن لغوشده قابل استفاده نمی‌ماند.
- لینک دعوت، شمارهٔ تلفن، پیوستن به گروه، اطلاعات کامل اعضا و ارسال پیام در
  این گام اضافه نشده‌اند. `Client` ایتایار همچنان بک‌اند جداگانه‌ای است.

## بررسی انجام‌شده

در ۱۷ اکتبر ۲۰۲۶ با سشن SDK موجود، اتصال مجدد، دریافت ۱۱ گفتگو، تبدیل هویت
هر ۱۱ گفتگو به InputPeer و resolve کانال عمومی `@eitaa` موفق بود. هیچ پیام یا
OTP ارسال نشد؛ نام‌ها، متن پیام‌ها، شناسه‌های خصوصی و توکن در شواهد ثبت نشدند.
حساب آزمایش‌شده پاسخ کامل داشت؛ صفحه‌بندی چندصفحه‌ای و بایگانی هنوز پذیرش
زندهٔ جداگانه می‌خواهند.

تست‌ها شامل پاسخ باینری، برخورد شناسهٔ کاربر و کانال، کش، min و hash مفقود،
تطبیق تاریخ با چت درست، پین، پوشه، صفحهٔ تکراری، محدودیت خروجی، نوسازی توکن،
سشن لغوشده و جلوگیری از OTP و retry ناخواسته‌اند.
