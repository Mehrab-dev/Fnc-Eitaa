# گام ۶ — رویدادهای اکانت

این لایه برای اجرای ربات روی اکانت شخصی است: برنامه به‌جای خواندن دستی تاریخچه،
رویداد `new`، `edit` و `delete` می‌گیرد. دریافت با polling انجام می‌شود؛ دورهٔ پیش‌فرض
۵ ثانیه است. این گام عملیات ویرایش یا حذف پیام را اجرا نمی‌کند؛ آن عملیات گام ۷ هستند.

## اولین تست

با سشن موجود اجرا کنید:

```powershell
python -m examples.account_updates --live --show-text
```

بعد از `Updates ready`، از برنامهٔ ایتا در پیام‌های ذخیره‌شده یک پیام تازه بفرستید.
باید خروجی `new` همراه با شناسه و متن ببینید. تست‌ها را جدا انجام دهید: ابتدا ارسال،
سپس بعد از مشاهدهٔ رویداد، ویرایش همان پیام و انتظار برای `edit`، سپس حذف و انتظار
برای `delete`. اگر ارسال و حذف بین دو نوبت polling اتفاق بیفتد، سرور ممکن است متن
اولیه یا تمام نسخه‌های میانی را نگه ندارد.

برنامه خودش پیام نمی‌فرستد و پیام‌ها را خوانده‌شده علامت نمی‌زند. برای توقف `Ctrl+C`
بزنید. وقتی متوقف است یک پیام آزمایشی دیگر بفرستید و همان دستور را اجرا کنید؛
با حفظ checkpoint باید تغییرات نگهداری‌شده در سرور دریافت شوند. متن فقط با
`--show-text` نمایش داده می‌شود؛ خروجی ترمینال را هم پیش از اشتراک بررسی کنید.

بررسی یک نوبت بدون انتظار دائمی:

```powershell
python -m examples.account_updates --live --once
```

اگر پس از شروع دوباره رویدادی دیده نشد، ابتدا برنامهٔ قبلی را متوقف کنید و سپس
این بررسی را اجرا کنید؛ فایل checkpoint را حذف نکنید:

```powershell
python -m examples.account_updates --live --once --common-only --diagnose
```

خروجی مشخص می‌کند checkpoint قبلی بارگذاری شد یا baseline تازه ساخته شد، نوع پاسخ
سرور و تعداد رویدادهای دریافتی/تحویلی چه بود و پاسخ‌های RPC چند update جانبی داشتند.
در ترکیب `--once --diagnose`، batch تأیید نمی‌شود و cursor دریافت جلو نمی‌رود؛ اگر
فایل از ابتدا وجود نداشته باشد baseline اولیه همچنان ساخته می‌شود. این گزینه به‌تنهایی
خطای ادامه را رفع نمی‌کند؛ برای تشخیص علت است. متن و توکن در log ساختاری چاپ نمی‌شوند.

در بررسی واقعیِ اولین مشکل ادامه، پیام زمان خاموشی در تاریخچه موجود بود و در کش
تحویل هم نبود، اما درخواست با pts ذخیره‌شده پاسخ خالی داد. درخواست با همان زمان و
pts یک واحد کمتر پیام را برگرداند؛ عقب‌بردن زمان به‌تنهایی آن را برنگرداند. علت داخلی
این رفتار سرور مشخص نیست. برای این حالت بازیابی صریح با هم‌پوشانی کوچک قابل اجراست:

```powershell
python -m examples.account_updates --live --show-text --replay-pts 1
```

`--replay-pts` فقط درخواست اول را عقب می‌برد؛ checkpoint دست‌کاری یا حذف نمی‌شود.
پس از پردازش و ack موفق، درخواست‌ها از وضعیت پاسخ سرور ادامه می‌یابند. در صورت خطای
حمل‌ونقل پیش از ack، همان هم‌پوشانی هنگام retry حفظ می‌شود. dedup موجود اعمال می‌شود،
اما رویداد قدیمی خارج از کش یا با نمایش متفاوت سرور ممکن است دوباره تحویل شود.
بازهٔ مجاز ۰ تا ۱۰۰۰ است و پیش‌فرض ۰ باقی مانده تا شروع معمول رویداد قدیمی تحویل ندهد.
این راهکار تضمین بازیابی هر شکاف یا اثبات صحت ادامهٔ خودکار پس از تمام توقف‌ها نیست.
برای بررسی بدون ack نیز می‌توان `--once --diagnose --replay-pts 1` داد.

اجرای بدون `--live` کاملاً آفلاین است. برای تست اولیه فقط چت‌های معمولی می‌توان
`--common-only` داد. مثال به‌صورت پیش‌فرض کانال‌ها و سوپرگروه‌های فهرست گفتگوها را
هنگام شروع کشف می‌کند. کانال مشخص با `--channel "@eitaa"` هم قابل افزودن است؛
در PowerShell نام کاربری را داخل کوتیشن قرار دهید.

## استفاده در برنامه

```python
import asyncio
from fnceitaa import AccountClient, Router

router = Router()

@router.on('new')
async def new_message(event):
    # برای اثرهای پایدار، event_id را در سیستم خودتان بررسی و ثبت کنید.
    print(event.kind, event.message_ids)

@router.on('edit')
async def edited_message(event):
    print('edited', event.message_ids)

@router.on('delete')
async def deleted_message(event):
    print('deleted', event.message_ids, event.peer)

async def main():
    async with AccountClient('account.eitaa') as client:
        updates = client.updates()
        await updates.initialize()
        await updates.watch_dialogs()
        await updates.run_polling(router)

asyncio.run(main())
```

ثبت هندلرها با `router.on('new'/'edit'/'delete'/'raw')` است. میان‌بر قدیمی
`Router.on_message()` متعلق به رویداد `message` در کلاینت قبلی است و اینجا استفاده
نمی‌شود. callbackها بیرون از قفل کلاینت اجرا می‌شوند و می‌توانند از کلاینت استفاده کنند.

برای کنترل دستی، `batch = await updates.poll()` بگیرید، تمام رویدادهای `batch.events`
را پردازش کنید و فقط پس از موفقیت `await updates.ack(batch)` را صدا بزنید. تا پیش از
ack، فراخوانی مجدد poll همان batch را برمی‌گرداند. `batch.has_more` یعنی صفحهٔ ادامه
وجود دارد؛ runner آن را بدون وقفهٔ معمول می‌گیرد. `updates.stop()` انتظار runner را
قطع می‌کند؛ پردازش batch جاری در صورت موفقیت پیش از خروج ثبت می‌شود.

## وضعیت، تحویل و محدودیت‌ها

- اولین اجرا از وضعیت جاری شروع می‌کند؛ تاریخچهٔ قدیمی به‌عنوان پیام جدید بازپخش نمی‌شود.
  وضعیت جدید هر کانال نیز هنگام اولین `watch_channel` پایه‌گذاری می‌شود.
- فایل پیش‌فرض `account.eitaa.updates` مستقل از سشن است. تغییرات وضعیت با فایل
  موقت، fsync و جایگزینی اتمیک ثبت می‌شوند. خطای نوشتن، خطای callback و لغو پیش از
  commit باعث جلو رفتن cursor نمی‌شوند. تغییر مشاهده‌شده توسط نویسندهٔ دیگر رد می‌شود؛
  این قفل بین‌پردازشی نیست: برای هر فایل فقط یک مصرف‌کننده/فرایند اجرا کنید.
- تحویل **حداقل یک بار** است. توقف پس از اثر callback و قبل از ack ممکن است همان
  رویداد را دوباره تحویل دهد. `event_id` ثابت و حافظهٔ محدود ۴۰۹۶ شناسه به کاهش تکرار
  کمک می‌کنند؛ تضمین exactly-once یا inbox تراکنشی نداریم. صف SQLite گام ۱۰ است.
- checkpoint شامل موقعیت‌ها، شناسهٔ مالک، access hash کانال‌ها و نگاشت محدود شناسهٔ
  پیام به مقصد است؛ متن پیام، شماره، OTP و توکن ورود در آن ذخیره نمی‌شوند. فایل را
  همراه سشن خصوصی نگه دارید؛ رمزگذاری نشده و در ویندوز مجوز پوشه را به ارث می‌برد.
- وضعیت عمومی و `pts` هر کانال جدا هستند. زمان انتظار پیشنهادی سرور برای کانال رعایت
  می‌شود. کانال‌هایی که بعداً به گفتگوها اضافه می‌شوند نیازمند اجرای دوبارهٔ
  `watch_dialogs()` یا `watch_channel(peer)` هستند؛ کشف دائمی عضویت پیاده نشده است.
  هیچ عضویت خودکاری انجام نمی‌شود؛ محدودیت دسترسی سرور همچنان اعمال می‌شود.
- `updateDeleteMessages` مقصد ندارد. اگر پیام قبلاً در رویدادها دیده شده باشد مقصد از
  نگاشت محدود بازیابی می‌شود؛ در غیر این صورت `event.peer` برابر `None` است. برای حذف
  کانالی مقصد از خود رویداد معلوم است. نگاشت حذف از تاریخچهٔ قبلی حدس زده نمی‌شود.
- تفاوت‌های نگهداری‌شده در سرور با `differenceSlice` و cursor کانالی بازیابی می‌شوند.
  اگر سرور `differenceTooLong`، تغییر وضعیت غیرقابل ادامه یا عقب‌گرد cursor بدهد،
  `UpdateGapError` می‌گیریم و checkpoint جلو نمی‌رود. حذف‌های از‌دست‌رفته را نمی‌توان
  با تاریخچه بازسازی کرد. پس از بررسی دستی وضعیت فعلی با تاریخچه، تنها در صورت پذیرش
  این شکاف، مسیر checkpoint تازه‌ای مثل `--checkpoint account.eitaa.resnapshot`
  انتخاب کنید؛ این کار baseline تازه می‌سازد و شکاف گذشته را بازیابی نمی‌کند.
- رویدادهای دیگر از مسیر `raw` در حافظه در دسترس‌اند. مثال CLI فقط سه نوع پیام را
  چاپ می‌کند. پیام رمزگذاری‌شده decrypt نمی‌شود؛ درخواست qts=-1 مطابق وب ایتاست.
- فقط خطاهای حمل‌ونقلِ خواندن و FLOOD_WAIT در runner دوباره امتحان می‌شوند. backoff
  حمل‌ونقل تا ۶۰ ثانیه و زمان انتظار اعلام‌شدهٔ سرور رعایت می‌شود؛ انتظار با stop
  قابل قطع است. خطای هندلر، سشن نامعتبر و خطای رمزگشایی متوقف‌کننده‌اند؛ OTP خودکار نیست.

## شواهد و پذیرش

مبنای پروتکل همان worker عمومیِ ثبت‌شده در manifest است، نه نسخهٔ جدید تلگرام:
`mtproto.worker-Zk-UnVZ2.js` با SHA256
`ef186db9dfa2a1e79ad30aadd805a5d455e90ee66b2827feca8006df979f4c17`.
در offsetهای کاراکتری 159980، 161944، 162245 و 169940 به‌ترتیب مسیر difference،
مدیریت کانال، RPC کانال و دریافت وضعیت اولیه دیده می‌شوند.

در ۱۷ اکتبر ۲۰۲۶، با سشن SDK موجود، `updates.getState`، `updates.getDifference` و
`updates.getChannelDifference` برای کانال عمومی ایتا پاسخ معتبر دادند؛ ذخیره و بارگذاری
checkpoint هم موفق بود. در این probe پیام تازه‌ای نبود و هیچ پیام/OTP/ویرایش/حذفی
ارسال نشد. کاربر سپس دریافت زندهٔ `new`، `edit` و `delete` را در پیام‌های ذخیره‌شده
تأیید کرد. در اولین تست ادامه پس از توقف، خروجی رویداد ظاهر نشد؛ علت هنوز مشخص نیست
و catch-up خودکار زنده تأیید نشده است. در بررسی فقط‌خواندنی بعدی، مسیر هم‌پوشانی یک
واحدی پیام آزمایشیِ زمان خاموشی را بازیابی کرد؛ batch تأیید نشد و checkpoint کاربر
بدون تغییر ماند. کاربر بعداً دریافت پیام ساخته‌شده در زمان خاموشی را با همین گزینه
تأیید کرد. اجرای دوبارهٔ دیگری برای اثبات ثبت ack و نبود بازپخش هنوز گزارش نشده است؛
ادامهٔ معمول بدون این گزینه نیز تأیید نشده است.
تست محلی شامل کدگذاری واقعی TL، replay و dedup، صفحه‌های ادامه، cursor مستقل
کانال، timeout، لغو، خطای handler، خرابی نوشتن و تعارض checkpoint است.
