# گام ۷ — ویرایش، حذف، فوروارد و کپی

گام ۶ تغییرات را دریافت می‌کند؛ در این گام برنامه خودش می‌تواند متن/کپشن را ویرایش
کند، پیام‌ها را حذف کند یا به مقصد دیگری فوروارد/کپی کند. پیاده‌سازی بر پایهٔ schema
پین‌شدهٔ وب ایتا با لایهٔ ۱۳۵ است. تست‌های محلی با پاسخ‌های TL و HTTP شبیه‌سازی‌شده
اجرا شده‌اند. کاربر ویرایش و خواندن متن جدید، فوروارد و خواندن مقصد، کپی و خواندن
مقصد، و حذف محلی و در دسترس نبودن پیام حذف‌شده را در چت خود تأیید کرده است.
نمایش کپی بدون نویسنده هنوز به‌طور قطعی تأیید نشده؛ مقصدهای دیگر نیز پذیرش جدا
می‌خواهند. عامل توسعه هیچ mutation واقعی روی حساب اجرا نکرده است.

## API

| متد | کاربرد و خروجی |
| --- | --- |
| `edit_message(peer, message_id, text, *, no_webpage=False)` | جایگزینی متن/کپشن؛ خروجی `AccountMessage` با تطبیق مقصد، شناسه و متن |
| `delete_messages(peer, message_ids, *, revoke=False)` | حذف یک دستهٔ ۱ تا ۱۰۰تایی؛ خروجی `DeletedMessages` |
| `forward_messages(to_peer, from_peer, message_ids, *, random_ids=None, silent=False)` | فوروارد دسته‌ای؛ tuple از `ForwardedMessage` به ترتیب ورودی |
| `forward_message(to_peer, from_peer, message_id, *, random_id=None, silent=False)` | فوروارد یک پیام و دریافت یک رسید |
| `copy_message(to_peer, from_peer, message_id, *, random_id=None, silent=False)` | فوروارد سمت سرور با `drop_author=True`؛ یک رسید |

همهٔ متدها روی `AccountClient` هستند. مقصد و مبدأ همان ورودی‌های `resolve_peer`
را می‌پذیرند. شناسه‌ها باید متعلق به مبدأ/مقصد مشخص‌شده باشند. `message_ids` یک
list یا tuple غیرخالی با حداکثر ۱۰۰ عدد یکتا و مثبت است. کتابخانه دسته‌ها را خودکار
نمی‌شکند؛ تقسیم خودکار می‌تواند در صورت خطا بخشی از عملیات را اجراشده باقی بگذارد.

ویرایش فعلاً متن ساده تا ۴۰۹۶ واحد UTF-16 را می‌پذیرد؛ entities قبلی را با فهرست
خالی جایگزین می‌کند. فایل پیوست عوض نمی‌شود و ویرایش رسانه، Markdown، زمان‌بندی و
کیبورد در این API نیست. مجوزها، مهلت ویرایش و محدودیت‌های حساب را سرور تعیین می‌کند.

حذف در چت کاربر/گروه معمولی با `messages.deleteMessages` انجام می‌شود. این RPC
پارامتر مقصد ندارد، بنابراین **قبل از ارسال حذف**، همهٔ شناسه‌ها با خواندن پیام‌ها
به چت انتخاب‌شده تطبیق داده می‌شوند. نبودن، حذف‌شدن یا تعلق هر پیام به چتی دیگر،
کل درخواست را پیش از mutation متوقف می‌کند. حذف کانال/سوپرگروه از RPC جداگانهٔ
`channels.deleteMessages` استفاده می‌کند. چون حذف آن اشتراکی است، در API باید صریحاً
`revoke=True` بدهید؛ `False` پذیرفته نمی‌شود. در سایر چت‌ها `False` حذف محلی و `True`
درخواست حذف برای طرف‌های دیگر است؛ تصمیم نهایی و مجوزها با سرورند. بررسی قبل از
عملیات، تراکنش اتمیک با سرور ایجاد نمی‌کند؛ پیام ممکن است بین خواندن و نوشتن تغییر کند.

رسید `DeletedMessages` شامل peer، شناسه‌های درخواست‌شده، revoke و pts/pts_count است.
`pts_count` تعداد قطعی پیام‌های حذف‌شده نیست؛ حتی صفر هم ممکن است پاسخ معتبر RPC
باشد. برای بررسی نتیجه، پیام یا تاریخچه را جدا بخوانید.

فوروارد/کپی هم مبدأ را قبل از mutation می‌خوانند. پیام سرویس یا پیام دارای
`noforwards` پذیرفته نمی‌شود؛ محدودیت‌های بیشتر سرور نیز اعمال می‌شوند. کپی از مسیر
ارسال مجدد متن یا دانلود/آپلود استفاده نمی‌کند و برای دور زدن حفاظت محتوا نیست.
آلبوم، ویرایش رسانه و انتقال فایل‌ها گام ۸ هستند. پشتیبانی عملی از انواع مدیا در
کپی/فوروارد باید جداگانه تست شود؛ وجود این flag در schema تضمین رفتار تمام مدیاها نیست.

هر `ForwardedMessage` شناسهٔ مقصد (`id`)، peer مقصد، `source_peer`،
`source_message_id`، `random_id` و `is_copy` دارد. `message` فقط وقتی خود پاسخ سرور
متن کامل مقصد را بدهد پر می‌شود؛ صرف نگاشت شناسه باعث ساخت متن یا اطلاعات مدیای
حدسی نمی‌شود. `is_copy` حالت درخواست را مشخص می‌کند. اگر پاسخ کامل کپی هنوز
`fwd_from` داشته باشد، پاسخ به‌عنوان کپی موفق پذیرفته نمی‌شود. رسید فقط شامل نگاشت
شناسه می‌تواند درخواست RPC را تأیید کند؛ نمایش نسبت‌دادن نویسنده در مقصد نیازمند
پذیرش زنده است.

## خطا و نتیجهٔ نامعلوم

هر mutation فقط **یک بار** ارسال می‌شود؛ token renewal، FLOOD_WAIT، retry و split
خودکار در مسیر نوشتن نداریم. خواندن مبدأ پیش از نوشتن از مسیر معمول خواندن و تمدید
توکن استفاده می‌کند. خطای آن خواندن هنوز به معنی عملیات نامعلوم نیست، چون نوشتنی
شروع نشده است.

پس از شروع نوشتن:

- خطای RPC صریح مانند نداشتن مجوز یا تغییرنکردن متن، به شکل `AccountRPCError` می‌آید.
  `MESSAGE_NOT_MODIFIED` به موفقیت ساختگی تبدیل نمی‌شود. سشن لغوشده مجوز را نامعتبر می‌کند.
- قطع اتصال، پاسخ نامعتبر/نامرتبط یا کنترل توکن، `MessageOperationUncertainError`
  می‌دهد؛ ممکن است سرور عملیات را انجام داده باشد. `operation`، `message_ids` و
  `random_ids` در خطا در دسترس‌اند؛ متن پیام و توکن داخل خطا نیستند.
- لغو asyncio پس از شروع نوشتن به شکل `MessageOperationCancelledError` است و همچنان
  زیرکلاس `asyncio.CancelledError` باقی می‌ماند. شناسه‌های بازیابی همراه خطا هستند.
- در فوروارد چندپیامی، نبودن نگاشت برای حتی یک random_id باعث نامعلوم‌شدن نتیجهٔ
  کل دسته می‌شود؛ ممکن است بخشی از پیام‌ها رسیده باشند. تکرار کورکورانه نکنید.

برای فوروارد/کپی قابل پیگیری، random_idهای یکتای غیرصفر signed 64-bit را پیش از
فراخوانی خودتان ذخیره و ارسال کنید. اگر ندهید کتابخانه آن‌ها را می‌سازد و در رسید
یا خطای نامعلوم برمی‌گرداند؛ توقف فرایند پیش از دریافت رسید همچنان ممکن است شناسهٔ
تولیدشده را از دسترس شما خارج کند. مدت یا تضمین حذف تکرار سمت سرور مشخص نشده است.
شناسه‌های عملیات نوشتن را با `event_id` دریافت رویدادها اشتباه نگیرید.

## تست محلی و پذیرش زنده، به ترتیب

ابتدا یک پیام آزمایشی در پیام‌های ذخیره‌شده بسازید و شناسه‌اش را از CLI بگیرید.
عدد `123` در دستورهای زیر نمونه است و باید با شناسهٔ پیام آزمایشی خودتان عوض شود.
برنامه بدون `--live` هیچ سشن/شبکه/پرسش تعاملی باز نمی‌کند. در اجرای زنده، پیش‌نمایش
عملیات نشان داده می‌شود و فقط پاسخ کامل `yes` آن را ارسال می‌کند.

۱. ویرایش:

```powershell
python -m examples.account_actions edit --live --peer self --message-id 123
```

متن جدید را وارد و پیش‌نمایش را تأیید کنید؛ خروجی `Edit confirmed` باید همان شناسه را
داشته باشد. سپس با `examples.account_messages read` متن جدید را بخوانید.

۲. فوروارد به خود:

```powershell
python -m examples.account_actions forward --live --from-peer self --peer self --message-id 123
```

شناسهٔ پیام مقصد باید از رسید خوانده شود؛ وضعیت نسبت‌دادن نویسنده را در ایتا بررسی کنید.

۳. کپی به خود:

```powershell
python -m examples.account_actions copy --live --from-peer self --peer self --message-id 123
```

محتوا و نبود برچسب نویسندهٔ فوروارد را در مقصد بررسی کنید. ابتدا با متن ساده تست کنید.

۴. حذف پیام آزمایشی، پس از تمام‌شدن تست‌های مبدأ:

```powershell
python -m examples.account_actions delete --live --peer self --message-id 123
```

خواندن دوباره و مشاهدهٔ مقصد برای تأیید لازم است. حذف اشتراکی در مقصد مجاز با
`--revoke` درخواست می‌شود. تا وقتی تست خودتان تأیید نشده، مقصد واقعی گروه/کانال را
برای آزمون حذف انتخاب نکنید. برای دستهٔ چندپیامی می‌توان چند شناسه بعد از
`--message-id` داد؛ edit و copy دقیقاً یک شناسه می‌گیرند. مقصد نام کاربری در PowerShell
باید کوتیشن داشته باشد، مانند `--peer "@example"`. شناسهٔ عددی مقصد ممکن است ابتدا
به `--load-dialogs` نیاز داشته باشد.

می‌توان listener گام ۶ را برای دیدن رویداد تغییرات در ترمینال دیگری باز گذاشت؛ آن
listener تأیید مستقل نتیجهٔ تمام عملیات نیست. مسیر `--replay-pts 1` برای ادامه پس
از توقف همان محدودیت‌های مستند گام ۶ را دارد.
