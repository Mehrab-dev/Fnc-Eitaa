# گام ۱ — شناخت پروتکل اکانت ایتا

تاریخ بررسی: ۱۵ اکتبر ۲۰۲۶.

وضعیت: شناخت اولیهٔ پروتکل برای شروع هستهٔ ارتباط انجام شد. ورود موفق، سشن
و عملیات اکانت هنوز پیاده یا تأیید نشده‌اند.

## کاربرد این گام چیست؟

برای ساخت یک کتابخانه شبیه fncbale، باید بدانیم برنامهٔ وب ایتا چطور درخواست‌ها
را به سرور می‌فرستد. این گام نقشهٔ آن ارتباط را فراهم می‌کند تا در گام بعد بتوانیم
فرستادن و خواندن درخواست‌های باینری را با پایتون بسازیم.

این خروجی هنوز قابلیت ورود به برنامه اضافه نمی‌کند؛ مشخص می‌کند چه چیزی باید
ساخته شود و برای کدام بخش‌ها شواهد واقعی داریم.

## چه چیزهایی مشخص شد؟

| بخش | یافته | کاربرد در کتابخانه |
| --- | --- | --- |
| انتقال | HTTP POST با بدنه و پاسخ باینری | ساخت transport مخصوص اکانت، جدا از ایتایار |
| قالب بیرونی | `eitaaObject`: توکن، شناسهٔ دستگاه، بدنهٔ درخواست، layer و flags | بسته‌بندی درخواست برای سرور |
| نسخه | لایهٔ مشاهده‌شده `135` است | جلوگیری از ترکیب قالب‌های ناسازگار |
| ورود | `auth.sendCode` و `auth.signIn`؛ همراه مسیر رمز دوم | طراحی ورود و مدیریت وضعیت OTP در گام ۳ |
| سشن | کد وب توکن و شناسهٔ دستگاه را نگه می‌دارد | طراحی سشن مستقل کتابخانه؛ بدون استخراج سشن مرورگر |
| تمدید | درخواست و پاسخ مخصوص تمدید توکن وجود دارد | جلوگیری از قطع دائمی ارتباط بعد از انقضا |
| خطا | هم خطای RPC و هم خطای مخصوص ایتا وجود دارد | تبدیل پاسخ‌ها به خطاهای مشخص پایتون |
| قابلیت‌ها | وجود نام یک متد در schema کافی نیست؛ کلاینت ۷۸ ورودی در فهرست عدم ارسال دارد | جلوگیری از وعدهٔ قابلیت‌های تأییدنشده |

در جدول API، **۴۴۳ ورودی متد و ۹۹۰ ورودی constructor** استخراج شده است.
این‌ها شمارش ورودی‌ها هستند؛ بعضی تکراری‌اند و همهٔ آن‌ها قابلیت قابل استفاده
یا تأییدشدهٔ سرور محسوب نمی‌شوند. ناسازگاری‌های schema بدون تغییر ثبت شده‌اند.

## چه چیزی روی سرور واقعی بررسی شد؟

یک درخواست `updates.getState` با **توکن خالی و شناسهٔ دستگاه ساختگی** به یکی
از سرورهای مشاهده‌شده فرستاده شد. هیچ شماره تلفن، OTP یا سشن واقعی ارسال نشد.

نتیجه:

- پاسخ HTTP برابر `200` بود.
- پاسخ ۲۴ بایتی بود و مطابق schema به خطای `401 / INVALID_LOGIN` تبدیل شد.
- پس قالب همین درخواست و پاسخ خطای آن با سرور واقعی سازگار بود.
- این آزمایش، ورود موفق یا دسترسی به اطلاعات اکانت را اثبات نمی‌کند.

## خروجی‌هایی که در پروژه داریم

- [گزارش فنی پروتکل](PROTOCOL.md): ترتیب فیلدها، شناسه‌ها، رفتار ورود و موارد نامشخص.
- [schema استخراج‌شده](../research/protocol/schema.json): جدول کامل نوع‌ها و متدها.
- [فهرست منتخب و سرورها](../research/protocol/inventory.json): متدهای مهم، متدهای مسدود و ناسازگاری‌ها.
- [شواهد کد عمومی](../research/protocol/evidence.json): بخش‌های مرتبط همراه محل آن‌ها در منبع.
- [نتیجهٔ بررسی زنده](../research/protocol/public_probe.json): بایت‌های درخواست و پاسخ بدون اطلاعات حساب.
- [اسکریپت استخراج](../scripts/extract_protocol.py): استخراج داده‌های ثابت بدون اجرای JavaScript دریافتی.

برای بررسی اینکه خروجی‌ها با منبع محلی تطبیق دارند:

```powershell
python scripts/extract_protocol.py --verify
```

فایل‌های JavaScript منبع در `research/` نگهداری محلی می‌شوند و در Git نادیده
گرفته شده‌اند. در checkout فاقد این فایل‌ها، تست بازتولید منبع skip می‌شود؛
تست snapshotها به فایل JavaScript وابسته نیست.

## گام بعد چه می‌سازد؟

گام ۲ هستهٔ پایتونی تبدیل داده به بایت و برعکس را می‌سازد: نوع‌های پایه، string،
bytes، vector، flags، فراخوانی متد و خواندن خطا. سپس قالب `eitaaObject` و ارتباط
HTTP اضافه می‌شود. معیار اولیهٔ آن، بازتولید همین درخواست ثبت‌شده و خواندن صحیح
همین پاسخ واقعی است؛ معیارهای بعدی شامل پاسخ‌های مرکب و محدودیت‌های decoder است.

این گام اکنون اجرا شده است؛ نتیجه و راهنمای استفاده در [گزارش گام ۲](ACCOUNT_STEP_2.md) قرار دارد.
